A Comparative Study of ChatGPT and Gemini}

\begin{abstract}
The rapid adoption of large language models (LLMs) in software development
makes it essential to rigorously validate the code they produce. This study
evaluates two state-of-the-art LLMs OpenAI ChatGPT (GPT-4o) and Google
Gemini 2.5 Pro on a carefully selected 30-problem subset of the
HumanEval-Java benchmark, spanning easy, moderate, and hard difficulty levels.
We used a semi-agentic workflow, we prompt each model to generate Java solutions,
transliterate the provided HumanEval base tests into JUnit~5/6, and then
systematically improve those tests through equivalence class partitioning and
boundary value analysis. Correctness is measured by pass/fail outcomes;
structural quality is assessed via JaCoCo branch coverage. ChatGPT (GPT-4o)
produced correct implementations for all 30 problems, while Gemini 2.5 Pro
succeeded on only 23 of 30, with failures attributable to off-by-one errors,
structural misinterpretations, and divergent edge-case contracts. Applying our
improved EC/BV-guided test suite achieved 100\% branch coverage across every
ChatGPT-generated class that contains conditional branches, demonstrating that
systematic black-box analysis substantially strengthens LLM-generated test
suites beyond the baseline.
\end{abstract}

\begin{IEEEkeywords}
LLM, code generation, test generation, HumanEval, JUnit, branch coverage,
equivalence class partitioning, boundary value analysis.
\end{IEEEkeywords}

\section{Introduction}
\label{sec:intro}

LLMs have transformed the way we build software, with developers being able to write code based on natural language prompts. Code-generating platforms such as ChatGPT and Gemini are able to create fully functional code automatically, saving developers considerable time and effort during the prototyping phase~\cite{yuan2025testctrl}. The validity and quality of the code created by LLMs are important factors that need careful consideration, hence the importance of conducting thorough testing procedures.

The HumanEval-X benchmark~\cite{peng2024humanevalxl}, a multilingual extension of the famous HumanEval coding test suite, offers a set of programming problems written in different natural and programming languages to evaluate the cross-language generalisability of code generation algorithms. Our case study revolves around the HumanEval-X Java sub-dataset, offering diverse problem scenarios ranging from easy string manipulation to algorithmic complexity.

Although LLMs are powerful tools today, some studies have already indicated that such systems are often prone to mistakes in dealing with edge cases, off-by-one issues, and cases involving complex reasoning~\cite{caracciolo2026guidelines}. Such behavior is particularly dangerous when using Java because of the strongly-typed nature of the language along with the requirement for explicit program control flow, which means that one wrong step might lead to incorrect results without producing any exceptions during runtime. While conducting this experiment ourselves, we concluded that correct results in terms of the smallest possible set of tests provided by HumanEval do not necessarily indicate correct logic.

Moreover, our methodological approach is grounded in reality. When a programmer working with an LLM-based assistant receives the code snippet generated by the machine learning model, they do not automatically trust its correctness and execute it right away. Rather, they inspect the output, perform testing, and continue iterating as long as there are any errors. To approximate such an interaction style, we use something that we refer to as a \textit{semi-agentic loop} -- a researcher in the loop workflow in which prompts are designed by the human observer based on the results of tests.

In this study, we pose two critical research questions: (1) How do recent iterations of ChatGPT and Gemini fare in terms of their performance on 30 HumanEval-Java tasks based on code correctness? (2) What are the failure modes of the weaker LLM, and what is the effect of a semi-agentic test-improvement feedback loop guided by test coverage metrics? The contribution of this work lies in a comprehensive comparative evaluation in which not only the pass/failure ratio but also the analysis in terms of line and branch coverage and test quality is performed. This appears to be one of the pioneering efforts that compare ChatGPT and Gemini on a task-specific benchmark for Java..

The rest of this paper is organized as follows. In Section~\ref{sec:method}, we discuss the methodology that we followed in conducting experiments, such as problem selection, code generation, prompt creation, and coverage measurement. We present our EC and BV analysis for selected problems in Section~\ref{sec:ec-bv-tables}. Section~\ref{sec:results} discusses our results quantitatively for both models. We discuss the failure modes of Gemini, the effectiveness of EC/BV testing, and the shortcomings of our method in Section~\ref{sec:discuss}. We conclude with our findings in Section~\ref{sec:conclude}.

\section{Methodology}
\label{sec:method}

\subsection{LLM Selection Rationale}
We have selected two models for comparison in this study—ChatGPT (GPT-4o) and Google Gemini 2.5 Pro. We chose ChatGPT because it is the leader of the industry and widely used in software engineering, while Google Gemini is one of Google’s most advanced models with multimodal functionality and strong code generation abilities \cite{caracciolo2026guidelines}.

The methodology we have used in our research is based on a \textit{semi-agentic} methodology, whereby a human author generates a prompt, captures the generated output of the LLM, tests it using a test suite, and manually analyzes the results to generate another prompt. This differs from agentic systems, where prompts are chained by the system itself and the results are automatically processed without human involvement, such as CoverUp~\cite{pizzorno2024coverup} and TestCTRL~\cite{yuan2025testctrl}.

\subsection{Problem Selection}
We selected 30 problems from the 164-problem HumanEval-Java
dataset~\cite{humaneval-x} covering three difficulty categories:

\begin{itemize}
\item \textbf{Easy (10)}: HE-000, 007, 009, 012, 021, 023, 024, 027, 028, 042
\item \textbf{Moderate (10)}: HE-003, 011, 014, 015, 017, 018, 025, 031, 034, 035
\item \textbf{Hard (10)}: HE-010, 040, 047, 055, 072, 083, 109, 126, 132, 139
\end{itemize}

Difficulty was assigned by inspection of the canonical solution complexity:
easy problems are one-pass linear algorithms on primitives or short strings;
moderate problems involve multi-branch conditionals or nested loops; hard
problems require non-trivial invariants, mathematical reasoning, or
multi-case boundary handling.

It was ensured that there were exactly ten questions in each tier of difficulties. We have also made sure that the total thirty questions cover a variety of different algorithmic patterns – from sorting algorithms to string manipulations to numerical computations, to name a few. This ensures that the two LLMs are compared for their performance in different kinds of logical reasoning.

\subsection{Prompt Design}
\label{sec:prompt}
The prompts for each code generation task were structured following a predetermined template format, thereby ensuring consistency across the two competing models. The template had three elements: (i) a role assignment statement directing the model to play the role of a Java programmer, (ii) the actual docstring of the HumanEval-Java task along with the example, and (iii) a directive to return only the implementation of the function/method without the enclosing class definition or \texttt{main} method code.

In generating tests, a distinct prompt was used, which comprised the original test base assertions rewritten into English, and the requirement to generate JUnit 5 \texttt{@Test} methods. For each iteration that corrected a failed test case, the prompt was augmented with the specific error message from the compiler or failed assertion, along with the corresponding input data and the actual output compared to the expected output. It was discovered that using all three was crucial for the model to generate a working implementation; otherwise, it would generate something else.

\subsection{Code Generation}
For each problem we issued the identical prompt (see
\texttt{logs/<llm>/HE-XXX\_codegen.md}) to both LLMs. The response was pasted
into the source tree without modification, per the assignment's constraint
at this step.

\subsection{Test Conversion and Improvement}
HumanEval's base tests are written as a single \texttt{main} that assembles
a list of boolean assertions. We transliterated each into JUnit 5/6 using
\texttt{assertTrue} with one assertion per original boolean (see
\texttt{*BaseTest.java}). Expected values were not changed.

For the improved suite we performed equivalence class partitioning and
boundary value analysis per problem (see
Section~\ref{sec:ec-bv-tables} and \texttt{report/equivalence\_classes.md})
and wrote targeted \texttt{@Test} methods, one per partition or boundary.

Our design philosophy for the enhanced test suites is that each technique should be treated as a black box. Partitions were defined strictly from the problem definition and not from the LLM’s generated implementation. In other words, the tests would identify any logical flaw in the code regardless of the choice of the algorithmic strategy used by the two models. Each problem was characterized by its inputs; these inputs were grouped into equivalence classes based on differences in behaviour, and a sample point from each class was chosen.

\subsection{Coverage Measurement}
Branch coverage analysis was done using JaCoCo 0.8.12. For each test suite run, we recorded the \texttt{jacocoTestReport} XML file output to get the number of missed and covered branches for each tested class. We mark all classes without any conditionals (such as \texttt{strlen}) as N/A because it is easy to reach 100\% branch coverage, even just by invoking a method.

We chose branch coverage over line coverage as our metric since the latter offers little value in terms of analyzing the test quality. While a test can easily cover 100\% of the lines, it does not necessarily mean that all branches have been reached; for instance, it can hit only one branch of a conditional statement by following one path through it.

\section{Equivalence Class and Boundary Value Analysis}
\label{sec:ec-bv-tables}

To illustrate the EC/BV process we applied across all 30 problems, we present two worked examples here: one from the moderate category and one from the hard category. These examples were chosen because they represent cases where the base HumanEval tests were insufficient and where our improved tests directly revealed Gemini defects.

\subsection{HE-018: howManyTimes}
The function \texttt{howManyTimes(String str, String substring)} calculates the number of occurrences of a certain substring in the provided string. There are two independent variables that define the input space, which are the size of \texttt{str} and the size of \texttt{substring}. The following table shows our discovered equivalence classes.

\begin{table}[h]
\centering
\caption{EC/BV Partitions for HE-018 (howManyTimes)}
\label{tab:ec-018}
\begin{tabular}{lll}
\toprule
Partition & Representative Input & Expected \\
\midrule
Empty string           & \texttt{("", "a")}      & 0 \\
Empty substring        & \texttt{("abc", "")}    & 0 \\
No match               & \texttt{("abc", "z")}   & 0 \\
Single match           & \texttt{("abc", "b")}   & 1 \\
Multiple non-overlapping & \texttt{("abab", "ab")} & 2 \\
Overlapping matches    & \texttt{("aaa", "aa")}  & 2 \\
Substring longer than string & \texttt{("ab", "abc")} & 0 \\
\bottomrule
\end{tabular}
\end{table}

The base HumanEval tests covered the ``single match'' and ``multiple non-overlapping'' partitions but omitted the empty substring and overlapping match cases. Gemini's implementation raised an exception when passed an empty substring, while ChatGPT correctly returned 0. This divergent edge-case contract was only revealed when we explicitly added the ``empty substring'' test case.

\subsection{HE-132: isNested}
The \texttt{isNested(String string)} function will return \texttt{true} if the provided string includes two nested brackets, such that the pattern is represented by \texttt{[[...]]} where the inner brackets are located inside the outer brackets. The table below includes the partitions that were obtained.

\begin{table}[h]
\centering
\caption{EC/BV Partitions for HE-132 (isNested)}
\label{tab:ec-132}
\begin{tabular}{lll}
\toprule
Partition & Representative Input & Expected \\
\midrule
Empty string            & \texttt{""}         & false \\
Single bracket pair     & \texttt{"[]"}       & false \\
Properly nested         & \texttt{"[[]]"}     & true  \\
Interleaved brackets    & \texttt{"([)]"}     & false \\
Multiple siblings       & \texttt{"[][]"}     & false \\
Deeply nested           & \texttt{"[[[]]]"}   & true  \\
Mixed nested and sibling & \texttt{"[[][]]"}  & true  \\
\bottomrule
\end{tabular}
\end{table}

The implementation for Gemini utilized a very basic counter approach where the number of opening and closing brackets was counted and allowed any string that had equal counts. "Interleaved brackets" and "siblings" partitions were not part of the base test cases and hence at first sight, the implementation seemed to be correct. The introduction of those cases rendered the implementation incorrect right away.

\section{Discussion}
\label{sec:discuss}

\subsection{Nature of Gemini Deviations}
Through thorough manual analysis, six unique categories of bugs were discovered to be the source of Gemini's errors; they all represented a particular weakness within the model's code generation capacity.
%
\begin{enumerate}
    \item \textbf{Missing palindrome check (HE-072 willItFly):} The model assumed that the palindrome checker would work in the reverse and compare method, but it did not take into consideration other aspects, including ignoring punctuation marks and spaces in determining if the string is a palindrome.
    \item \textbf{Off-by-one in loop bound (HE-040 triplesSumToZero, HE-139 specialFactorial):} In both cases, there is an incorrect use of the loop condition \texttt{i < n} or \texttt{i <= n}, resulting in the omission of the final number in the sequence that would otherwise contribute to a valid triplet or factorial sum.
    \item \textbf{Incorrect closed-form (HE-083 startsOneEnds):} Gemini tried to employ a mathematical formula to count the total number of integers that began and ended with 1 between two integers. Unfortunately, the mathematical formula did not hold true for higher exponents. The solution worked only for small integers.
    \item \textbf{Structural misinterpretation (HE-132 isNested):} For the nested bracket problem, Gemini simplified the issue into a basic bracket counter that counted the total number of open and close brackets. The model did not consider the fact that brackets of differing types cannot be interleaved; thus, it accepted \texttt{([)]}.
    \item \textbf{Stream filter masking equality (HE-000 hasCloseElements):} In the stream-based approach, Gemini’s filter had a logic flaw in the equality of indices, which led to the omission of pairs whose difference in absolute values equaled the required distance. The error was quite tricky and went unnoticed because of the initial set of test inputs.
    \item \textbf{Divergent edge-case contract (HE-018 empty substring):} In the generated program, getting an empty substring resulted in an error, although the problem statement implied that getting an empty substring should result in returning an empty string. This discrepancy was only exposed by equivalence class testing.
\end{enumerate}

All these flaws indicate that the faults of Gemini do not occur randomly but rather follow a pattern, with most of them related to boundary cases, mathematics, and the accurate understanding of implicit contracts in problem statements. This phenomenon is in line with other studies in the realm of evaluating LLMs, in which models have often failed edge cases despite solving the regular case accurately.

\subsection{Effectiveness of EC/BV Partitioning}
Equivalence class (EC) and boundary value (BV) partitioning significantly strengthened the test suites beyond the baseline HumanEval tests. For HE-132, the provided sample tests only covered a single ``well-nested'' partition; our manually derived equivalence classes added a ``siblings'' partition where two adjacent braces of different kinds appear, which immediately exposed the bracket-counter flaw. Similarly, for HE-018, the edge-case contract divergence described above was not exercised by any HumanEval base test; it was only when our BV analysis tested string lengths of zero that Gemini's misinterpretation came to light. Thus, for at least these two problems, EC/BV partitioning proved strictly stronger than the default test set, demonstrating its value even when the initial code appears correct on the surface.

More broadly, the average branch coverage improvement for ChatGPT (from 95\% to 100\%) illustrates that even for a well-performing model, there are code paths that the baseline tests simply do not reach. The fact that our improved tests achieved perfect branch coverage for ChatGPT without any additional knowledge of the implementation confirms that black-box test design techniques - when applied systematically - are powerful enough to saturate coverage even against unknown implementations.

\subsection{Refactoring Iteration}
For all Gemini failures, member C used a feedback-based refactoring approach. For each bug, on average, two iterations of feedback were sufficient to identify the right solution; however, for the most problematic bugs (namely, the interpretation mistake in HE-132 and the stream filter bug in HE-000), it took three iterations to find the right solution. In general, the best prompting strategy proved to be offering the model (i) a short description of the failing test, (ii) a comparison between the actual output and the expected one, and (iii) an idea regarding the specific location of a possible problem (such as ``pay attention to the loop bound for \texttt{n = 0}''). Simply asking both systems to fix the program code without those hints usually resulted in cosmetic changes, not in finding the right solution. Both LLMs could make the necessary adjustments once the problem was identified, but ChatGPT did not need any refactoring at all.

This phenomenon has practical implications for those developers who use language models as coding assistants, as they should be aware that when the code provided by the model is incorrect, it is just as important to provide an appropriate second prompt as to provide an appropriate first one. More specifically, a well-structured and accurate feedback message that provides failing cases and correct outputs works much better than an indirect request for corrections.

\subsection{Limitations}
There are certain constraints associated with our research that should be taken into account while evaluating its outcomes. First of all, although the sample consisted of 30 problems that showed some diversity, it could not encompass the complete variety of coding issues that exist. The comparison between just two LLMs was conducted and was made via their chat interfaces, which means that we did not have any influence on the generation parameters such as temperature, seed, or version. The semi-agentic workflow is quite realistic yet incorporates an element of subjectivity, since each researcher might phrase their prompt differently. Finally, test improvements for a single round and coverage were evaluated, and a completely automatic iterative process would show even better results.

\subsection{Threats to Validity}
Beyond the general limitations discussed above, we identify the following threats to the validity of our conclusions.

\textbf{Internal validity.} Since both the models were asked questions using the interactive interface of chat, there is a chance that similar prompts may yield different results in subsequent runs because of non-deterministic sampling. To address this issue, we accepted the output generated by each model on the first run, only repeating the process if a fault was found. Nevertheless, we cannot promise consistency in the event of repetition of the experiment.

\textbf{Construct validity.} We rely on branch coverage as our first indicator of the quality of tests. Although branch coverage is a highly reputable structural criterion, it does not include mutation adequacy and semantic validity. It is possible for a test suite to reach 100\% branch coverage but fail to detect significant logic flaws. We need to integrate branch coverage with mutation testing for more comprehensive results in the future.

\textbf{External validity.} Our conclusions are specific to the HumanEval-Java benchmark and the two models evaluated. They may not generalise to other programming languages, problem domains (e.g., systems programming or data-intensive applications), or newer model versions. In particular, both ChatGPT and Gemini are updated frequently, and the gap we observed between them may narrow or reverse in future releases.

\section{Conclusion}
\label{sec:conclude}

In this work, we conducted an experimental analysis of the two latest LLMs, namely ChatGPT (GPT-4o) and Google Gemini 2.5 Pro, on a Java subproblem set of the HumanEval-X benchmark involving 30 problems. Following a semi-agentic procedure that simulates real-life application development scenarios, we coded up the solution to each problem, converted the initial base tests into JUnit 5/6 format, and systematically increased their complexity by applying equivalence class partitioning and boundary value analysis techniques. We have found that there is a significant difference in the performance of the two models, with ChatGPT solving all the problems correctly, and Gemini failing to solve 7 out of them.

In terms of testing, we have found that although the baseline HumanEval tasks provide useful initial filtering, they alone are not enough to ensure the correctness of the LLMs' solutions. The improved test suite guided by EC and BV reached 100\% branch coverage for all classes generated by ChatGPT with conditional statements and discovered an unnoticed bug in the solution of HE-018 by Gemini. This shows that structured black-box testing is feasible and valuable as a supplementary measure to the benchmark tests.

Regarding future directions, there are plans to extend this research in multiple ways. First, an attempt will be made to automate the semi-agentic loop by feeding the output from JaCoCo and JUnit to the model automatically rather than relying on the manual prompt-and-repair cycle to evaluate whether automation improves upon our current approach in terms of the quality of generated test suites. Second, the study will be extended to consider the whole set of 164 problems from the HumanEval-Java benchmark as well as other large language models such as GitHub Copilot and Meta LLaMA to have a better overview of where things stand at the moment. Finally, adding mutation testing to the list of quality metrics used could be beneficial.
